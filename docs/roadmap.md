# 生产架构路线图

## 从 150 条文档扩展到 1,000 万条记录

保留 PostgreSQL 作为事务元数据和权限边界，在规模增长后将向量检索分层：按业务域、产品和时间建立分区或逻辑租户；使用 HNSW/量化索引和只读副本承载查询；通过批处理队列异步生成 Embedding；对历史冷数据使用对象存储、Iceberg 或专用向量检索集群。索引构建与切换采用版本化索引，避免更新过程中读取半成品。

查询路径先通过租户、产品、有效年份等过滤条件缩小候选集，再执行 Dense + Sparse 检索和重排序。超过单库容量或吞吐上限后，按租户或业务域路由到多个检索分片，使用统一的检索 API 汇总结果。

## 数据时效性与缓存

政策更新进入带版本号的知识库写入队列，完成校验、Embedding、索引更新和审核后才发布为 active 版本。政策撤回使用软删除和版本状态，保留审计记录。高频查询可以在 Redis 中缓存规范化查询、过滤条件、知识库版本和模型版本对应的最终结果；政策发布或模型切换时按版本号自然失效，避免全量删除缓存。

## 数据治理与 PII 防护

知识库和客户会话分离存储。进入检索链路前执行 PII 检测和脱敏，生产日志默认不记录完整客户号码、身份证件或账户信息。数据库采用最小权限账户、行级安全策略、加密连接和密钥轮换；API 通过 JWT/OAuth2 进行租户和角色授权，并在检索前执行权限过滤。所有文档变更、查询主体、结果版本和管理员操作写入不可篡改审计日志。

## 可靠性与可观测性

对 Embedding、检索、重排序和缓存分别记录耗时、错误率、命中率、结果版本和模型版本。设置 P50/P95/P99 延迟、空结果率、检索 Recall 抽样和过期政策命中率告警。模型或索引发布采用灰度和回滚机制，定期使用标注查询集回归测试。
